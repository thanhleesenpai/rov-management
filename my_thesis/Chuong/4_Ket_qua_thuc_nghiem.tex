Chương này trình bày quá trình hiện thực hóa hệ thống từ thiết kế kiến trúc đến xây dựng giao diện và kiểm thử. Nội dung gồm bốn phần chính: (1)~thiết kế kiến trúc và cơ sở dữ liệu; (2)~hiện thực các chức năng cốt lõi kèm minh họa giao diện; (3)~kiểm thử chức năng, tải và hiệu năng; (4)~mô hình triển khai đề xuất.

\section{Thiết kế kiến trúc hệ thống}
\label{section:4.1}

\subsection{Kiến trúc tổng quan}

Hệ thống được thiết kế theo kiến trúc \textbf{Client-Server đa tầng}, kết hợp mô hình \textbf{Microservice thu nhỏ} để tách biệt bộ phận nhận diện hình ảnh nặng nề khỏi máy chủ chính. Ba tầng chính gồm: (1)~tầng trình bày (React SPA), (2)~tầng nghiệp vụ (Node.js), và (3)~tầng dữ liệu (MongoDB Atlas).

\begin{figure}[H]
  \centering
  \includegraphics[width=0.92\textwidth]{../Hinhve/arch_tong_quan.png}
  \caption{Kiến trúc tổng quan hệ thống quản lý ROV}
  \label{fig:arch_tong_quan}
\end{figure}

Như Hình~\ref{fig:arch_tong_quan}, frontend được phân phối qua Vercel CDN và giao tiếp với backend Node.js thông qua REST API. Backend đảm nhận toàn bộ nghiệp vụ: xác thực JWT, quản lý hàng đợi Bull, xử lý file S3 và điều phối các dịch vụ ngoài (Gemini API, YOLOv8 Microservice, Nominatim). Cơ sở dữ liệu MongoDB Atlas hoạt động độc lập trên cloud.

\subsection{Sơ đồ phụ thuộc module}

Hình~\ref{fig:arch_module_dep} thể hiện sự phân chia module phía backend theo nguyên tắc \textit{high cohesion, low coupling}. Mỗi thực thể nghiệp vụ (Projects, Trips, Media, Sensor, DVL, Sonar, Snapshots, Notifications, AI, Audit) có bộ tệp độc lập gồm \texttt{routes.js}, \texttt{controller.js}, \texttt{service.js}, \texttt{model.js}. Controller không chứa logic nghiệp vụ; Service là trung tâm xử lý duy nhất.

\subsection{Mô hình triển khai đề xuất}

Do giới hạn phần cứng (YOLOv8 cần khoảng 1,5\,GB RAM, không có GPU), hệ thống chưa được triển khai lên VPS trong khuôn khổ đồ án. Mô hình triển khai đề xuất (Hình~\ref{fig:arch_deploy}) sử dụng Docker Compose để đóng gói bốn dịch vụ trên một VPS duy nhất: \texttt{nginx} (reverse proxy), \texttt{node-backend} (Express API + Bull Workers), \texttt{yolo-service} (FastAPI + YOLOv8n), \texttt{redis} (JWT blacklist + hàng đợi). Frontend được deploy riêng trên Vercel CDN; cơ sở dữ liệu ở MongoDB Atlas; file media trên AWS S3.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.90\textwidth]{../Hinhve/arch_deploy.png}
  \caption{Mô hình triển khai đề xuất trên VPS}
  \label{fig:arch_deploy}
\end{figure}

Phương án này giúp đơn giản hóa vận hành: một lệnh \texttt{docker compose up} khởi động toàn bộ hệ thống. Redis chạy cùng VPS đảm bảo độ trễ dưới 0,5\,ms cho JWT blacklist, tránh chi phí dịch vụ Redis trả phí.

\subsection{Sơ đồ tuần tự các luồng nghiệp vụ chính}

Hai sơ đồ tuần tự dưới đây mô tả chi tiết tương tác giữa các thành phần hệ thống cho hai luồng nghiệp vụ quan trọng nhất: tải lên dữ liệu cảm biến và phân tích YOLO bất đồng bộ.

\subsubsection{Luồng tải lên dữ liệu cảm biến CSV}

Hình~\ref{fig:seq_sensor_upload} mô tả luồng tải lên dữ liệu cảm biến từ khi Operator chọn file đến khi dữ liệu được lưu vào MongoDB và bản đồ GPS được cập nhật.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.95\textwidth]{../Hinhve/seq_sensor_upload.png}
  \caption{Sơ đồ tuần tự — luồng tải lên file CSV cảm biến}
  \label{fig:seq_sensor_upload}
\end{figure}

Luồng gồm sáu bước chính: (1)~Frontend parse file CSV phía client, validate định dạng (bắt buộc timestamp và depth, các trường còn lại tùy chọn) trước khi gửi lên server; (2)~\code{POST /trips/:id/sensor-data} gửi mảng readings kèm tên file gốc (\texttt{sourceFile}); (3)~Controller kiểm tra sourceFile đã tồn tại trong DB chưa — nếu có thì xóa data của file đó trước (re-upload), nếu là file mới thì kiểm tra overlap theo timestamp lớn nhất hiện có và cắt bỏ dữ liệu trùng; (4)~\texttt{SensorData.insertMany()} ghi batch toàn bộ readings hợp lệ; (5)~Nếu dòng đầu tiên có tọa độ \texttt{lat/lng}, hệ thống gọi Nominatim reverse geocoding để lấy tên địa danh và cập nhật \code{trip.gpsLocation + trip.locationName}; (6)~Trả về \texttt{\{count, total, warning?\}} — frontend hiển thị toast xanh (thành công), vàng (overlap\_trimmed hoặc file\_skipped).

\subsubsection{Luồng phân tích YOLO bất đồng bộ qua Bull Queue}

Hình~\ref{fig:seq_ai_analysis} mô tả luồng phân tích nhận diện vật thể: Operator kích hoạt từ AIAnalyzePopover, backend trả ngay HTTP 202, Bull Worker xử lý nền và SSE đẩy kết quả về khi xong.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.95\textwidth]{../Hinhve/seq_ai_analysis.png}
  \caption{Sơ đồ tuần tự — luồng phân tích YOLO bất đồng bộ qua Bull Queue}
  \label{fig:seq_ai_analysis}
\end{figure}

Luồng gồm bảy bước: (1)~Operator chọn model và ngưỡng confidence trong popover, nhấn ``Run Analysis''; (2)~\texttt{POST /media/:id/analyze\allowbreak{} \{model, confidence\}} đến backend; (3)~\code{mediaService.enqueueAnalysis()} cập nhật \code{media.analysisStatus = 'pending'}, \texttt{labels = []} rồi thêm job vào hàng đợi \texttt{mediaAnalysisQueue}; (4)~Backend trả HTTP 202 ngay lập tức — giao diện người dùng không bị chặn; (5)~Bull Worker lấy job: tạo presigned GET URL (TTL 10 phút) để YOLO service tải file từ S3, gọi \texttt{POST yolo-service:\allowbreak{}8000/detect \{mediaUrl,\allowbreak{} model, confidence\}}; (6)~YOLO service tải file từ S3, chạy inference (ảnh: 1 lần, video: lấy mẫu thích nghi 0,2--1,0 giây/khung tùy độ dài), trả mảng \texttt{labels[]\{name, confidence,\allowbreak{} bbox, frameTime, trackId\}}; (7)~Worker lưu kết quả, đặt \code{analysisStatus = 'done'}, gọi \texttt{notifService.create()} để đẩy SSE về client — frontend nhận event, invalidate query \texttt{['media']} và labels xuất hiện mà không cần tải lại trang.

Thiết kế bất đồng bộ này đảm bảo trải nghiệm người dùng mượt mà: phân tích video dài có thể mất 5--15 phút nhưng giao diện không bị đóng băng. Nếu YOLO service không phản hồi (\texttt{ECONNREFUSED}), Worker ghi \code{analysisStatus = 'failed'} mà không crash queue.

\section{Mô hình triển khai (đề xuất)}
\label{section:4.5}

Do yêu cầu phần cứng của YOLOv8 (1,5 GB RAM), hệ thống chưa triển khai lên VPS trong phạm vi đồ án này. Mô hình triển khai đề xuất được thiết kế để dễ dàng thực hiện khi có hạ tầng phù hợp.

\textbf{Cấu hình đề xuất:}
\begin{itemize}[leftmargin=*, topsep=4pt, itemsep=2pt]
  \item \textbf{Frontend:} Vercel (CDN toàn cầu, deploy tự động từ git push).
  \item \textbf{Backend VPS:} Contabo 4 vCPU / 4 GB RAM / ~6 USD/tháng, chạy Ubuntu 22.04.
  \item \textbf{Docker Compose:} 4 service — \texttt{nginx:alpine} (reverse proxy + SSL), \texttt{node-backend} (Express + Bull Workers), \texttt{yolo-service} (FastAPI + YOLOv8n CPU), \texttt{redis:alpine} (~30MB RAM).
  \item \textbf{Database:} MongoDB Atlas M0 (free tier, 512MB).
  \item \textbf{Storage:} AWS S3 ap-southeast-1 (pay-per-use, gần như miễn phí với traffic demo).
  \item \textbf{AI:} Gemini 2.5 Flash qua Google AI Studio API (free tier 1500 request/ngày).
\end{itemize}

Cách triển khai: \texttt{git clone} lên VPS, tạo \texttt{.env}, chạy \texttt{docker compose up -d}. Nginx tự động cấp SSL/TLS qua Let's Encrypt và điều hướng: \texttt{/api/v1/*} → Node.js:5000, còn lại → Vercel fallback.

\textbf{Ước tính chi phí hàng tháng:} VPS \$6 + MongoDB Atlas \$0 + AWS S3 <\$1 + Gemini \$0 = \textbf{~\$7/tháng} — hoàn toàn khả thi cho môi trường demo và thử nghiệm thực địa.
